01

What you are looking at

A user talks to Streamlit. Streamlit calls FastAPI with a JWT. FastAPI runs a master LangGraph. The supervisor picks a specialist (RAG, SQL, web, or general). The RAG specialist runs a nested CRAG graph: dense Chroma + BM25 FTS5 → RRF → knowledge-graph boost → cross-encoder → grade → optional rewrite → context. Claude then token-streams the answer over SSE. Guardrails, cache, rate limits, audit logs, and optional traces wrap that turn.

  1. Auth. Authorization: Bearer <jwt>. Missing/invalid → 401. Rate limit exceeded → 429.
  2. Session. Empty question → 400. If session_id exists and belongs to another user → 404. Else reuse or mint session_<uuid>.
  3. Keepalive. First SSE line is : keepalive so the UI is not stuck while models load.
  4. Cache. Redis key rag:answer:{user_id}:{sha256(normalized question)}. Hit skips the graphs (fail-open if Redis is down). Bypassed for order traffic, confirmation phrases, and any turn with a pending order draft; checkpoint-inspection errors also bypass, so a stale answer can never stand in for a live order turn.
  5. Master graph (get_master_agent_graph, compiled once). Checkpointer is AsyncPostgresSaver on DATABASE_URL. thread_id is the session id. Metadata includes user_id for ownership.
  6. Input rails. Length cap 10k. Jailbreak denylist always. NeMo injection when enabled and ready. Presidio on input when spaCy loads.
  7. Long-term memory load. Up to 10 user_memories rows for this user_id.
  8. Supervisor. Cheap keyword router first; LLM agenerate_structured(SupervisorDecision) if ambiguous. After one specialist this turn, next hop is FINISH. Cap max_iterations=2 plus a 60-second wall clock on ainvoke. A pending order draft pins the turn to sql_agent only when the message is a confirmation, cancellation, or draft detail — unrelated questions still route normally.
  9. RAG specialist. Nested graph with skip_generate=True and skip_memory_persist=True, thread_id="{session}:rag" so checkpoints do not collide. Retrieve is pre-filtered by user_id. Fallback tool: document_search.
  10. SQL / order specialist. Model-written SQL against application tables is disabled. The specialist calls typed order tools only: get_order, list_orders, order_analytics, and the approval-gated create_order / update_order. Intent comes from a Pydantic OrderIntentV1 at temperature 0; a schema failure keeps the draft untouched and asks again.
  11. Web / general. Web reads an explicit URL through the SSRF-guarded read_web_page, otherwise Tavily (if TAVILY_API_KEY) or DuckDuckGo. General uses deterministic calculate / current_datetime when the request matches, then Claude. Every call goes through invoke_tool, which overwrites user_id with the authenticated subject, enforces requires_approval, and audits the call.
  12. Synthesize, then output rails. Tokens are buffered until the rails pass, so blocked or anonymized text never reaches the client mid-stream. Specialist answers that are already final (SQL, web, general, empty-context RAG) stream verbatim; grounded RAG answers get one generate_stream pass over fenced, untrusted context.
  13. SSE done. session_id, question, answer, iterations, agent_trajectory, guardrail_metadata.
  14. Save memory. Background thread extracts ADD/UPDATE/IGNORE (semantic / episodic allowed) into Postgres.
  15. Audit / metrics / traces. audit_event (no raw PII). inc_chat(ok|cache|blocked|error). LangSmith if tracing env is set. Langfuse if keys are set.

SSE event shapes

typeMeaning
tokenIncremental Claude text (content)
doneFull payload; UI stores session_id
errorTransport or upstream failure. A safety block is not an error: it sends a safe token plus a normal done

Agent tools (scoped per specialist)

app/tools/registry.py holds one allowlist per agent in AGENT_TOOL_NAMES. A specialist asks for a tool through get_tool_for_agent(agent, tool), so a tool that is not on that agent's list is never returned — cross-agent reach is a lookup failure, not a policy note.

What every call passes through

  • Tenant identity is injected, not requested. invoke_tool overwrites user_id with the authenticated subject for every tenant-scoped tool and raises when there is no authenticated user. user_id is hidden from the JSON schema the model sees, so it cannot be chosen by a model argument.
  • Writes need explicit approval. requires_approval tools return a refusal string unless the caller passes approved=True, which only the verified confirmation branch does.
  • Every call is audited. tool.call, tool.done, tool.error, and tool.denied record the tool name and session without payloads.
  • The web reader is pinned. The hostname is resolved once, non-global addresses (including IPv4-mapped and NAT64 forms), credentials in the URL, and cloud metadata hosts are rejected, and the request connects to that validated IP with TLS hostname verification. Redirects re-run the same check, capped at three hops and 1 MB.
⛔

Model-written SQL against application tables is disabled. The SQL specialist answers general database questions with a refusal and reaches order data only through the typed repository methods above, so users, documents, and checkpoint tables are unreachable from chat.

Order workflow (human confirmation)

Orders live in their own SQLite file (ORDER_DATABASE_URL, default data/orders_demo.db under the project root) and never mix with Postgres application state. Writes are two-step: the agent drafts, the human confirms with an exact phrase, and only that verified branch executes.

Draft lifecyclepending_order_action in the LangGraph checkpoint
stateDiagram-v2
    [*] --> collecting: write intent detected
    collecting --> collecting: detail supplied, still incomplete
    collecting --> awaiting_confirmation: all fields present, payload sealed with hash
    awaiting_confirmation --> awaiting_confirmation: plain yes, or wrong action id
    awaiting_confirmation --> executed: confirm order act_xxxxxxxx
    awaiting_confirmation --> cancelled: cancel order act_xxxxxxxx
    collecting --> expired: 15 minute TTL
    awaiting_confirmation --> expired: 15 minute TTL
    executed --> [*]
    cancelled --> [*]
    expired --> [*]

    participant U as User
    participant API as POST /chat/
    participant SQL as sql_agent

    participant DB as orders_demo.db

    U->>API: create an order for two widgets
    API->>SQL: route (cache bypassed)

    U->>API: ship it to 1 Main Street

    SQL-->>U: summary plus type confirm order act_1a2b3c4d

    DB-->>SQL: order row (idempotent on replay)
    SQL->>CP: clear pending_order_action
    SQL-->>U: confirmed and executed

Pending action record

FieldWhy it exists
action_idThe exact token the user must repeat; a mismatch never executes
user_id / session_idBinds the draft to one tenant and one thread; another session cannot confirm it
tool_namecreate_order or update_order only
payload / payload_hashThe reviewed values and their seal. If the payload changes after review, confirmation is refused
missing_fieldsDrives the precise follow-up question instead of a generic retry
phasecollecting or awaiting_confirmation; a sealed draft stops absorbing edits
expires_at15-minute TTL, checked before every action
idempotency_keySession, action, and payload digest, so a duplicate confirmation returns the same order

Storage guarantees

ConcernHow it is handled
Tenant isolationEvery repository query filters on user_id; a foreign order id simply returns nothing
Concurrent updatesUPDATE … WHERE version = expected_version; rowcount != 1 means no write and a stale-version answer
Duplicate createsUnique (user_id, idempotency_key), integrity-error replay returns the committed row, and a reused key with different values is rejected
SQLite concurrencyWAL, busy_timeout, foreign keys on, and NullPool (StaticPool in memory)
Demo datapython -m database.seed_orders --user-id <id> writes 30 deterministic days; re-running is idempotent

Audit trail

Each stage emits a structured event with the action id and tool name and no address or line-item payload: order.draft_created, order.details_required, order.confirmation_required, order.confirmation_denied, order.draft_cancelled, order.draft_expired, and order.write_executed.

✋

A plain “yes” never writes. Neither does a confirmation with the wrong action id, from another session, after expiry, or against a draft whose payload changed after you reviewed it.

Non-negotiables

  • Chat = POST /chat/ SSE token / done only.
  • One supervisor + hybrid RAG specialist. No basic-RAG toggle.
  • Sessions = session_<uuid>.
  • Retrieval tenant filter happens before search, not after.
  • Each specialist may only call the tools on its own allowlist; user_id is injected from the JWT, never chosen by the model.
  • Order writes execute only after the exact confirm order <action_id> phrase from the same user and session, against an unchanged payload.
  • No model-written SQL runs against application tables.
  • Tokens are buffered until output guardrails pass.
  • Product UI in Docker is port 8002; local run.py UI is 8501.
